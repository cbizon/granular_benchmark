# Qualitative evaluation rubric

Rubric version: `1.0`

## Purpose

This rubric evaluates what an agent actually built, how faithfully it
reproduces the reference simulations, and how it used its available time. It
complements the deterministic metrics in `evaluation/results.json`; it does
not replace or recalculate them.

The review is a gated scorecard, not a single weighted score. The simulation
type is established first. Criteria that require an event-driven hard-sphere
implementation are not applicable to other model classes. A continuum model
that resembles Figure 1 visually must remain distinguishable from a faithful
event-driven molecular-dynamics implementation.

## Evidence rules

Use this evidence order:

1. Executed source code and generated artifacts.
2. Deterministic harness metrics and rendered comparisons.
3. Tests and recorded test output.
4. Provider transcript, commands, and tool output.
5. Manifest descriptions and the agent's final narrative.

Do not accept an implementation description or final claim when it conflicts
with code or artifacts. Separate direct observations from inferences. Every
applicable judgment requires evidence with a file path, transcript location,
metric name, or rendered artifact reference.

The reviewer may compare the implementation with the paper, associated
references, and the C code. It must distinguish:

- behavior required by the paper;
- behavior implemented by the C code;
- an alternative implementation that is physically and numerically
  equivalent;
- a deviation that changes the modeled system.

Different correct event-queue implementations are possible. Record queue and
cell architecture descriptively before judging correctness.

## Rating anchors

Each criterion uses one rating:

- `correct`: Convincingly and completely satisfies the criterion.
- `mostly_correct`: Substantially correct, with limited deficiencies.
- `mostly_incorrect`: Some relevant implementation exists, but major
  deficiencies affect correctness or interpretation.
- `incorrect`: Missing, contradicted by evidence, or fundamentally wrong.
- `uncertain`: Available evidence is insufficient for a defensible judgment.
- `not_applicable`: The criterion does not apply to the classified model.

For visualization, the renderer may map the first four ratings to `3`, `2`,
`1`, and `0`. It must render `uncertain` and `not_applicable` separately and
must not calculate a composite score across model classes.

## 1. Simulation classification

Classify the primary implementation before applying later sections:

- `event_driven_hard_sphere`: Particle free flight is advanced exactly between
  discrete hard-contact events.
- `time_stepped_hard_sphere`: Individual hard particles are advanced on
  discrete timesteps rather than between predicted events. Contacts retain
  hard-contact impulse laws and are handled by collision detection,
  projection, constraints, or other nonsmooth contact methods.
- `soft_sphere_time_stepped`: Particle contacts are represented by finite
  overlap, forces, and discrete timesteps.
- `continuum_or_wave`: The primary state is a field or wave equation rather
  than individual particle dynamics.
- `synthetic_or_prescribed_patterns`: Particle or field outputs are generated
  from prescribed patterns, fitted wavelengths, interpolation, or other
  kinematic construction rather than the claimed physical simulation.
- `hybrid`: Multiple model classes materially contribute to the submitted
  trajectories.
- `other`: A different identifiable method.
- `uncertain`: The method cannot be established from available evidence.

Record all material components, not only the primary type. Determine whether
the submitted files were generated by the implementation, postprocessed from
it, or synthesized independently.

## 2. Event-driven hard-sphere fidelity

Apply this section only when event-driven hard-sphere dynamics are a material
component.

### Delayed particle states

Determine whether particle positions and velocities are stored at their last
update times and advanced lazily to an event time. Identify eager global
updates, mixed strategies, or state inconsistencies. Check that collision
prediction and response use states evaluated at the same physical time.

### Virtual cells and neighbor handling

Determine whether virtual cells are implemented and used correctly. Record the
actual cell strategy, cell-crossing behavior, neighbor enumeration, particle
membership updates, and treatment near hard walls. An alternative exact
neighbor-search strategy may be physically valid but is not an implementation
of the requested virtual-cell method.

### Event scheduling

Characterize the event queue, candidate-event representation, invalidation
strategy, version counters or equivalent mechanism, tie handling, and
rescheduling after collisions. Look for stale events, duplicate events,
nonadvancing event times, missed cell crossings, and event-order dependence.

### Free flight and collision prediction

Check exact free flight under gravity, particle-particle collision roots,
stationary sidewall collisions, moving-plate collision roots, top-boundary
handling if present, and safeguards against selecting roots in the past.

### Collision response

Check normal restitution, tangential friction, rotation, moments of inertia,
Walton-style sticking/sliding behavior, wall and plate response, and consistent
use of the plate velocity. Distinguish physical driving by the moving plate
from any numerical rebound floor that adds energy to weak impacts.

### Dense-layer behavior

Determine whether collision rates reach numerical noise, event times stop
advancing, overlaps appear, or the event queue grows pathologically. Assess
whether the implementation detects and reports these failures.

## 3. Figure 1 result fidelity

Apply this section to every model class. Review every case separately.

Use the deterministic harness comparison for:

- contrast;
- dominant wavelength;
- `Q2`, `Q4`, and `Q6`;
- temporal phase and subharmonic order;
- integer-cycle alignment;
- reference and candidate representative frames.

Visual judgment should address pattern identity, orientation, defects,
coarsening, phase, boundary influence, and whether the flat case is actually
flat. Do not infer physical correctness from visual resemblance alone.

## 4. Physical fidelity

Apply this section to every model class. Compare phase-resolved and full-profile
behavior with the C code:

- center-of-mass height;
- layer depth;
- mean and RMS translational velocity;
- mean and RMS spin;
- rotational kinetic energy;
- particle, wall, and plate collision rates;
- precision-qualified particle, wall, and plate overlaps.

Record cases where agreement is obtained through fitting or prescribed output
rather than through the submitted dynamics.

## 5. Numerical treatment and regularization

Inventory every identified mechanism and its parameters. Classify whether it
is physically motivated, a numerical regularization, energy injecting, energy
dissipating, neutral, or uncertain.

For event-driven implementations, explicitly check:

- velocity-dependent restitution;
- collisions made elastic below a velocity threshold;
- minimum rebound velocity or other energy addition at plate collisions;
- event-time epsilons or forced time advancement;
- event-rate cutoffs;
- overlap projection or positional correction;
- collision suppression or batching.

For soft-sphere implementations, explicitly check timestep, stiffness,
damping, friction, overlap correction, force clipping, velocity clipping, and
stability criteria.

For continuum, wave, synthetic, or hybrid implementations, identify fitted
wavelengths, prescribed modes, filtering, numerical diffusion, forcing, and
hard-coded case-specific behavior.

Assess whether the treatment changes the physical interpretation, conceals
failure, or is clearly disclosed.

## 6. Tests and engineering evidence

Inventory tests and determine whether they are substantive or merely output
schema checks. Event-driven implementations should normally include:

- analytic two-particle collision response;
- particle-particle collision-time prediction;
- sidewall and moving-plate collision tests;
- rotational and frictional collision tests;
- delayed-state consistency;
- virtual-cell membership and crossing;
- event invalidation and sequencing;
- simultaneous or nearly simultaneous events;
- dense-layer and inelastic-collapse regression;
- determinism or controlled seed behavior;
- end-to-end trajectory generation.

Soft-sphere implementations should test force laws, timestep convergence,
overlap bounds, dissipation, and stability. All implementations should test
output contracts, reproducibility, and at least one end-to-end case.

Also assess code readability, unnecessary case-specific logic, scalability,
and whether performance claims are supported.

## 7. Reproducibility, authenticity, and compliance

Determine:

- whether all submitted cases can be regenerated from documented commands;
- whether seeds and parameters are recorded;
- whether the same physical engine produced all cases;
- whether outputs were generated by the submitted code;
- whether final claims match code, tests, and artifacts;
- whether limitations were identified honestly;
- whether transcript evidence indicates access to prohibited implementations.

Do not infer cheating from similarity alone. Report direct evidence and leave
provenance uncertain when history or transcript evidence is absent.

## 8. Transcript narrative and time use

Produce a short chronological narrative covering:

- reading and algorithm selection;
- major implementation decisions;
- simulation launches and waits;
- important failures and pivots;
- validation and finalization;
- subscription limits, retries, and restarts.

Do not report private chain-of-thought. Do not label provider API duration as
exact thinking time.

Where supported, report:

- `provider_inference_seconds`: Provider-reported API or inference duration.
- `agent_action_seconds`: Time executing foreground tools and commands.
- `external_job_wait_seconds`: Wall-clock intervals waiting for simulations or
  other background jobs.
- `subscription_wait_seconds`: Runner backoff or provider-limit waits.
- `unclassified_seconds`: Elapsed time not defensibly assigned.

State whether intervals overlap. Prefer a harness-generated timeline over
reviewer arithmetic. If timestamps are incomplete, return `null` and explain
the limitation instead of inventing a value.

## 9. Overall synthesis

Assign one algorithm tier:

- `faithful_event_driven`
- `event_driven_with_minor_deviations`
- `event_driven_with_major_deviations`
- `non_event_driven_particle_model`
- `continuum_or_synthetic_model`
- `hybrid_or_other`
- `unclassifiable`

Summarize strengths, major failures, and the bottom line. The bottom line must
lead with what kind of simulation was built and whether it is a faithful
implementation of the requested method. Do not collapse algorithm fidelity,
scientific agreement, engineering quality, and efficiency into one score.
